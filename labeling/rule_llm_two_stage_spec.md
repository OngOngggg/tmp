# 规则候选 + LLM复核：离线与在线定义

## 1. 标签要分两层

不能把“规则命中”直接叫作“应该弹窗”。建议使用三个不同概念：

- **候选（candidate）**：宁可多召回，送入第二阶段；目标是高 Recall。
- **LLM确认（confirmed）**：LLM判断此刻是否值得给学生一个低打扰帮助；目标是提高 Precision。
- **最终展示（shown）**：再经过冷却、焦点、提交/判题等待、用户关闭等保护后真正展示。

因此长时间无输入可以是 candidate=1，但不应直接等于 shown=1。

## 2. 候选规则

取多个规则的并集，而不是只依赖一个idle阈值：

1. 长时间停顿：`idle >= 30s && keys_30s < 5`；
2. 失败后停滞：最近一次判题为 WA/CE/TLE/MLE，且之后有编辑后再次停顿；
3. 近期编辑后暂停：`10s <= idle < 30s && text_keys_30s >= 1`；
4. 反复修改/运行：短时间内多次执行或多次局部修改后没有继续推进；
5. 异常行为：连续退格、光标来回移动、行列变化明显但文本增长很少。

长idle规则承担召回职责，不能单独承担“该打扰”的语义。

## 3. LLM如何处理误报

LLM输入只包含窗口结束之前的信息：候选触发原因、5/10/30/60/120秒特征、按键摘要、代码回放、最近一次已知判题状态，以及是否处于提交/判题等待。

要求输出固定JSON：

```json
{"decision":"show|suppress|uncertain", "confidence":0.0, "reason":"..."}
```

- `show`：近期有实质编辑并停滞，或失败后没有推进迹象；
- `suppress`：仍在输入、剪贴板/快捷键为主、正在等待判题、明显只是阅读/检查；
- `uncertain`：仅有idle，无法区分卡住和正常思考。

`uncertain`默认不立即弹窗，但进入抽样日志，供后续标注和规则改进。

## 4. 漏报不能只靠第二阶段LLM解决

如果LLM只复核规则触发的窗口，它看不到规则没有召回的漏报。需要三条补充机制：

1. **规则并集**：不同类型的高召回信号并行生成候选；
2. **低比例全量扫描**：例如每个session随机抽取5%未触发窗口交给LLM，估计候选集外漏报率；
3. **主动补充标注**：优先标注规则漏报样本，把新模式加入候选规则，再用独立时间段验证。

论文中应分别报告：

- 候选召回率：人工正例有多少进入候选；
- LLM确认Precision/Recall：在候选及抽检样本上的结果；
- 最终展示率和误打扰率：经过冷却、等待状态和用户关闭保护后的线上指标。

## 5. “长时间没结果”的边界

如果“没结果”指**判题请求已经发出但结果尚未返回**，应设置`judge_pending`并直接抑制提示；否则会把网络延迟误判为学习困难。

如果“没结果”指**学生长时间没有新的运行/提交反馈，同时也没有继续编辑**，则可以进入高召回候选，由LLM判断是卡住、读题、检查还是离开页面。

这两个状态在日志中必须分开，不能只用一个`idle`字段代替。
