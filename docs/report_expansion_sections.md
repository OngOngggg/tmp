# 汇报可补充内容：把“两阶段方案”讲完整

## 一、先修正当前稿中的三个口径问题

### 1. 数据量

当前是从约100个clean session中，每个session抽取5个时刻，形成500条窗口，不是500个session。

### 2. 69条“该提示”的含义

69条是面向高召回候选策略的标签口径，其中46条长idle窗口是按候选策略恢复的。它更适合称为“候选正例”，不宜直接称为独立人工金标准。

因为长idle候选本身参与了标签调整，再用idle规则评价这套标签会产生循环定义。因此候选口径下得到的Precision 56.8%、Recall 91.3%、F1 70.0%只能用于检查候选策略覆盖情况，不能作为最终模型性能。

### 3. AI指标

56.8%、91.3%、70.0%不是AI标注结果，而是候选口径下主规则的Precision、Recall和F1。

在新版候选标签和AI都给出确定二分类标签的340条窗口中，AI结果为：

- 一致率：82.4%；
- Cohen's kappa：0.172；
- AI正例Precision：60.0%；
- AI正例Recall：14.3%；
- AI正例F1：23.1%。

这说明当前AI仍然偏保守，不能把它描述成已经解决了漏报问题。

## 二、把研究问题拆成三个RQ

### RQ1：候选识别

与单一idle规则相比，融合多尺度行为、代码进展和运行/提交上下文，能否提高帮助候选时刻的召回率？

### RQ2：误打扰控制

在保持较高候选召回率的情况下，LLM二次判断能否有效区分“卡住”和“思考、检查、等待、离开”等状态，从而减少误提示？

### RQ3：系统代价与实际可用性

与纯规则和全量LLM判断相比，两阶段方法能否降低每个session的误提示次数、LLM调用量、响应延迟和成本？

如果后续能够开展在线实验，可增加：

### RQ4：在线效果

两阶段主动提示是否能缩短学生恢复有效编程活动的时间，同时不显著提高关闭、忽略和主观打扰率？

## 三、不要只做“困难/不困难”，拆成两个判断维度

当前二分类容易把两个不同问题混在一起：

1. 学生是否可能需要帮助；
2. 学生当前是否适合被打扰。

建议将最终决策写成：

```text
帮助需求：是否缺少进展、反复失败或出现异常调试行为
                         ＋
可打扰性：是否仍在输入、是否等待判题、是否失焦、是否刚恢复活动
                         ↓
动作：立即显示 / 延迟观察 / 抑制提示
```

这样可以解释以下边界情况：

- 长时间没有进展：帮助需求可能较高，但可打扰性不确定，先进入候选；
- 学生连续输入：即使代码有错误，当前也不适合打断；
- 判题尚未返回：可能需要帮助，但当前应等待；
- 失败后修改并再次停顿：帮助需求和可打扰性都较高，可以考虑提示。

LLM不直接输出“弹/不弹”，而是输出状态和动作：

```json
{
  "state": "struggling|thinking|checking|waiting|away|uncertain",
  "need_help": 0.0,
  "interruptible": 0.0,
  "action": "show|delay|suppress",
  "reason": "..."
}
```

## 四、方法上增加“进展停滞”，不要只统计按键多少

Dong等（2021）的核心不是简单idle，而是“在典型时间内是否取得显著进展”：

- 使用代码状态变化衡量进展；
- 用进展量的25%分位定义显著进展；
- 用取得显著进展所需时间的75%分位定义典型时间；
- 超过典型时间仍没有显著进展，才视为挣扎候选。

本文可以借鉴这一思想，增加“距上一次有意义进展的时间”：

```text
有意义进展 = 代码结构发生有效变化
          或 测试通过数增加
          或 错误类型得到改善
          或 完成一次有效运行/提交
```

然后构造：

- `time_since_progress`：距离上一次有意义进展的时间；
- `code_change_rate`：单位时间代码有效变化量；
- `edit_efficiency`：文本编辑量与光标/快捷键/删除操作量之比；
- `failure_persistence`：相同错误或失败结果持续的次数；
- `repeat_run_no_change`：无代码变化的重复运行次数；
- `small_edit_after_failure`：失败后只做极少修改又进入停顿；
- `personalized_idle_zscore`：当前停顿相对于该学生此前停顿分布的异常程度；
- `task_idle_percentile`：当前停顿相对于同题其他学生的分位位置。

这会把方法从“固定30秒阈值”提升为“任务/学生自适应的进展停滞检测”。

当前历史数据无法完整恢复AST、测试通过数和每次运行结果时，可以先用文本键、行列变化和代码快照差异近似；在线采集阶段再记录完整代码快照和运行事件。

## 五、候选规则应当是多种事件的并集

Pu等（2025）并不是只使用30秒idle，而是用了六类主动触发：idle、代码块完成、程序执行、多行修改、代码注释和持续选中。398次主动干预中，53.3%有效参与、12.1%被认为是打断、34.7%被忽略；其中idle触发效果最差，约一半被忽略。

Tabarsi等（2022）也使用了多种挣扎检测器，包括超过5分钟无动作、少量修改、无修改重复运行和低活动量。

因此本文候选生成可以写成：

```text
C(t) = 长idle
    OR 失败后停滞
    OR 近期编辑后突然暂停
    OR 无修改重复运行
    OR 局部反复修改
    OR 长时间没有有意义进展
```

每一种候选要保留`trigger_type`，分别统计覆盖率和误打扰率。这样可以回答“究竟是哪类规则有用”，而不是只报告一个混合结果。

## 六、正确表述LLM处理误报和漏报

不能写成“LLM对规则的误报漏报进行复核”。在线阶段并不知道哪些是误报和漏报，而且LLM如果只看到规则命中的窗口，就看不到漏报。

建议改成：

> 第一阶段使用多个行为规则的并集生成高召回候选；第二阶段使用LLM结合代码和上下文抑制候选中的潜在误报。对于规则未覆盖的漏报，通过未触发窗口抽检、第二检测器和主动补充标注进行发现，再迭代候选规则。

漏报发现机制：

1. 从规则未触发窗口中随机抽取5%～10%交给LLM或第二标注者检查；
2. 估计候选集之外的正例比例；
3. 总结漏报对应的行为模式；
4. 加入新的候选规则；
5. 在新的session或时间段上重新验证。

## 七、补充完整的对比实验和消融实验

### 方法对比

|编号|方法|作用|
|---|---|---|
|B1|30秒idle规则|最简单基线|
|B2|多规则并集|高召回候选基线|
|B3|逻辑回归/XGBoost|验证手工特征能否被轻量模型组合|
|B4|LLM直接判断全部窗口|语义能力上限及成本对照|
|M1|高召回规则 + LLM复核|本文主要方法|
|M2|M1 + 上下文保护和冷却|最终系统策略|

### 消融实验

1. 单一30秒窗口 vs 5/10/30/60/120秒多尺度；
2. 去掉运行/提交/判题上下文；
3. 去掉代码回放，只使用行为特征；
4. 去掉LLM，只保留规则；
5. 固定idle阈值 vs 学生/题目自适应阈值；
6. 去掉冷却和每session次数限制；
7. LLM只读代码 vs LLM同时读取行为摘要和触发原因。

### 数据划分

- 按`solution_id`或学生划分训练、验证和测试，不能随机拆窗口；
- 阈值只能在训练/验证集选择；
- 最终测试集在确定方案前保持不可见；
- 如果题目数量允许，增加按题目留一验证，观察跨题泛化能力。

## 八、评价指标不能只放Precision、Recall和F1

主动提示系统还应报告：

- Candidate Recall：人工正例有多少进入规则候选；
- Final Precision/Recall/F1：经过LLM复核后的最终判断；
- PR-AUC：类别不平衡时比Accuracy更有意义；
- False Prompts per Session：每个session平均误提示次数；
- Candidate Rate：每小时生成多少候选；
- Suppression Rate：LLM和保护规则抑制了多少候选；
- LLM Call Reduction：相对于全量LLM调用减少多少；
- 平均/P95延迟；
- 每100个session的API成本；
- `show/delay/suppress`的置信度校准；
- 按session进行bootstrap置信区间，而不是把500个窗口当独立样本。

如果目标明确偏向高召回，可以把主指标写成：

> 在Candidate Recall不低于90%的条件下，比较各方法的最终Precision、每session误提示数和LLM调用量。

这比单纯比较最高F1更符合你的系统目的。

## 九、标注设计还应补一个重要修正

标注页面不能展示窗口结束后才发生的最终判题结果。当前数据中的`judge`需要核实它是“窗口时刻之前最近一次已知结果”，还是“整个solution的最终结果”。如果是后者，标注者会受到未来结果影响，形成后见之明。

建议新标注页只展示：

- `last_known_judge_before_t`；
- `judge_pending`；
- 截止`t`的代码和行为；
- 当前候选的触发类型。

同时把标注问题拆成三步：

1. 截止当前是否缺少进展？
2. 当前是否适合被打扰？
3. 应立即显示、延迟观察，还是抑制？

AI预标注结果应在人类完成初始判断后再显示，避免锚定效应。

## 十、在线实验可以从shadow mode升级为小规模随机验证

第一阶段只做shadow mode，记录候选触发后学生是否自然恢复输入、运行或提交。

第二阶段可在LLM确认候选中随机分配：

```text
50% 显示低打扰提示
50% 暂不显示，作为对照
```

观察：

- 到下一次有效编辑/运行/提交的时间；
- 提示点击、忽略和关闭；
- 提示后是否立即恢复输入；
- 是否撤销或拒绝AI建议；
- 后续判题是否改善；
- 学生主观打扰程度。

这样才能区分“系统判断和人工一致”与“提示实际上有帮助”。Pu等（2025）的53.3%有效参与、12.1%打断和34.7%忽略可以作为在线结果的参照维度，但不能直接作为同任务基准。

## 十一、可以凝练出的研究贡献

不要把贡献写成“提出一个idle规则”，可以写成：

1. 构建了面向在线决策的严格因果多尺度编程行为窗口，避免使用未来事件；
2. 将帮助时机拆分为“帮助需求”和“可打扰性”，显式区分卡住、思考、检查、等待和离开；
3. 提出高召回行为候选与LLM语义复核相结合的两阶段框架；
4. 在统一数据上比较规则、轻量模型、全量LLM和两阶段方法的准确性、误打扰、延迟与成本；
5. 设计候选外抽检和在线反馈机制，使规则漏报能够被持续发现和修正。

其中第2、3、4点决定这项工作是否不只是一个简单规则原型。
