# 在线编程帮助时机识别：阶段性汇报（修订版）

## 一、研究问题

现在的编程学习系统已经能够解释报错、生成提示，甚至直接给出代码。但在实际使用中，还有一个更靠前的问题：**什么时候应该主动提供帮助？**

学生暂时没有输入，不一定表示遇到困难，也可能是在读题、思考算法、检查代码、观察运行结果，或者已经离开。只根据“多久没有按键”弹窗，容易把正常思考误判为卡住，造成打扰。

因此，本阶段暂时不研究“提示内容怎么生成”，而研究：

> 能否根据学生当前已经发生的编程行为，识别可能需要帮助、并且当前适合提示的时刻？

这里需要区分三个概念：

1. **Candidate（候选时刻）**：行为上可能存在帮助需求，值得进一步检查；
2. **Confirmed（确认时刻）**：结合代码和上下文后，判断提示可能有价值；
3. **Shown（展示时刻）**：通过冷却、焦点、运行状态等保护策略后，真正向学生展示提示。

长时间没有输入可以成为 Candidate，但不能直接等同于 Shown。

## 二、研究定位和拟解决的不足

已有研究通常从编译错误、测试失败、暂停、按键延迟或最终成绩推断学生是否挣扎。这些信号有价值，但“学生现在是否适合被主动打扰”是一个更细的窗口级决策：同样的长暂停，可能是卡住，也可能是思考、检查或等待判题。

本研究的定位不是提出一个新的 idle 阈值，而是建立一个**严格因果、可解释、可部署的帮助时机识别流程**：

- 用行为轨迹构建窗口，而不是只看最终成绩；
- 同时表示短期活动和较长任务上下文；
- 将“需要帮助”和“适合打扰”分开；
- 保留“不确定/跳过”类别，避免强行给模糊样本贴二分类标签；
- 比较规则、轻量模型、LLM 和两阶段方法在识别效果、打扰风险与系统代价上的取舍。

## 三、整体流程：离线验证与在线部署

```text
                           离线阶段
原始 OJ 行为数据 ──→ clean session 筛选 ──→ 严格因果窗口构建
                                                ↓
                                         多尺度行为特征
                                                ↓
                                  人工标注、AI预标注与质量检查
                                                ↓
                           规则 / 轻量模型 / LLM 统一离线评估
                                                ↓
                                确定候选生成器和保护策略
                                                │
                                                │ 部署候选检测逻辑
                                                ↓
                           在线阶段（拟设计，先 shadow mode）
学生行为 ──→ 实时事件采集 ──→ 更新多尺度特征
                              ↓
                       高召回规则或轻量模型生成 Candidate
                              ↓
                 运行、提交、失焦、剪贴板、等待判题等上下文过滤
                              ↓
                  LLM或轻量模型判断：卡住 / 思考 / 检查 / 等待 / 不确定
                              ↓
                   立即提示 / 延迟观察 / 静默记录 / 抑制
                              ↓
       记录提示关闭、忽略、恢复输入、运行、提交和判题结果
                              ↓
                      新数据回流，补充标注并更新离线评估
```

当前先采用 shadow mode：系统照常计算候选点，但暂不打扰学生，只记录候选出现的频率及候选后的行为。确认触发频率和误打扰风险后，再做小规模在线提示实验。

## 四、数据和窗口构建

从已有 OJ 按键数据中筛选约 100 个 clean session，当前筛选条件为：

- session 持续时间不少于 60 秒；
- 有效按键数不少于 30 次；
- 按键时间、光标位置等字段可以正常解析；
- 同一个 solution 只保留一次。

每个 session 建立约 5 个观察窗口，共生成 500 条 prototype windows。每条窗口具有：

- 唯一 `window_id`；
- `solution_id`；
- `event_index`；
- `window_end_time`；
- 题目、判题和可用上下文信息；
- 窗口结束前的行为特征；
- 按键摘要和代码近似回放。

### 严格因果约束

窗口结束时间记为 `t`。在线系统在 `t` 时只能使用已经发生的事件：

```text
event.time < t
```

窗口结束后的按键、运行、提交和判题结果不能用于生成当前触发判断。`t` 之后的事件只用于事后分析，例如学生是否恢复输入、是否运行或提交，不能反过来参与标签和特征计算。

此外，如果原始数据里的 `judge` 是整个 solution 的最终结果，就不能直接把它当作 `t` 时刻已知信息。在线实现应优先使用：

- `last_known_judge_before_t`；
- `judge_pending`；
- `run_count_before_t`；
- `submit_count_before_t`。

### 多尺度窗口

对同一个时刻分别回看 5、10、30、60 和 120 秒：

- **5 秒**：观察刚刚发生的连续输入和即时修改；
- **10 秒**：观察短暂停顿前后的局部活动；
- **30 秒**：作为低活动和短期停滞的主要观察范围；
- **60 秒**：观察此前是否仍处于持续编写或调试状态；
- **120 秒**：补充较长任务上下文，避免只看到最后一段静止状态。

这些时间尺度是当前原型的设计参数，并非声称某篇文献已经证明 5/10/30/60/120 秒最优。后续通过消融实验比较单窗口和多尺度窗口。

## 五、特征设计及文献依据

当前特征不是照搬单篇论文，而是将不同研究中反复出现的行为信号放到同一个因果窗口中。

| 本文设计 | 相关研究启发 | 当前处理 |
|---|---|---|
| 编译错误、连续失败、重复尝试 | Jadud（2006）、Tabanao 等（2008）用编译错误刻画困难；Schwartz 等（2025）使用测试失败和异常尝试次数定义挣扎 | 作为困难证据；但只使用 `t` 前已经返回的运行/提交结果 |
| 按键间隔和停顿 | Leinonen 等（2016）分析按键延迟；Tabarsi 等（2022）包含超过 5 分钟无动作的检测器 | 统计停顿次数、总时长、P90、当前连续 idle 时长 |
| 代码状态和编辑过程 | Carter 等（2015、2017）研究编程状态转移；Dong 等（2021）按时间顺序查看 trace 评估进展/挣扎 | 使用按键、光标行列变化、退格、代码回放和进展停滞特征 |
| 主动帮助与打断代价 | Horvitz 与 Apacible（2003）讨论上下文和打断代价；Pu 等（2025）比较多类主动触发方式 | idle 只作候选信号，并加入运行、提交、失焦、剪贴板和冷却策略 |
| LLM 辅助判断 | Hellas 等（2023）、Koutcheme 等（2024）显示 LLM 能处理编程反馈，但与人工判断并不完全一致 | LLM 作为候选点的二次判断器或对照方法，不直接替代人工真值 |

除已有特征外，后续可补充：

- 近期活动量与较长窗口活动量之比；
- 当前 idle 相对于学生个人典型 idle 的偏离程度；
- 代码长度净变化、新增/删除行数和修改后恢复原样比例；
- `time_since_meaningful_progress`，即距离上一次有意义代码进展的时间；
- 无修改重复运行、小改动后再次失败、连续失败次数；
- 是否刚完成代码块、刚粘贴多行代码、刚收到判题结果；
- 最近编辑是否长期集中在同一行或同一局部区域。

## 六、标签与数据质量

当前存在多个标签口径，汇报时不能混为一个“准确率”。建议按用途报告：

### 1. 全量人工窗口标签

500 条 prototype windows 的人工完成标签为：

| 标签 | 数量 |
|---|---:|
| 该提示 | 90 |
| 不该提示 | 290 |
| 不确定/跳过 | 120 |

排除不确定标签后有 380 条确定二分类样本。但 84 个有确定标签的 session 中，有 38 个 session 的窗口全部被标成同一类别，说明部分标注可能受到“这道题整体应该怎样”的影响，尚不能把这批标签视为无误差 gold label。

### 2. 高召回候选口径

经过边界复核后，另有一套 69/297/134 的候选标签口径，用于讨论长 idle 是否应进入候选集。它适合分析候选覆盖，不适合再用来证明 idle 规则本身有效，否则会产生“因为长 idle 才改成正例，再用长 idle 证明召回率高”的循环定义。

### 3. 独立人工评估子集

早期用户导出的 235 条标签中，有 182 条为确定二分类：正例 61 条、负例 121 条，来自 39 个 session。当前较适合作为规则主基线的结果来自这套子集，因为它与后续高召回候选口径分开。

### 4. AI 辅助标签

AI 对 500 条窗口的判断为：

| AI 标签 | 数量 |
|---|---:|
| 该提示 | 18 |
| 不该提示 | 338 |
| 不确定 | 144 |

在当前候选标签和 AI 都给出确定二分类的 340 条窗口上：一致率 82.4%，Cohen's kappa 约 0.17；AI 正例 Precision 约 60.0%，Recall 约 14.3%，F1 约 23.1%。AI 判断明显偏保守，适合作为预标注或二次筛选，不适合作为第一阶段高召回检测器，也不能替代人工真值。

下一步应抽取 100～150 条窗口，由第二名标注者独立标注，报告 Cohen's kappa；对分歧样本进行仲裁，并重点复核整题同标签的 session。

## 七、当前离线结果

在 235 条人工导出标签中的 182 条确定二分类样本上，规则消融结果如下：

| 规则 | Precision | Recall | F1 |
|---|---:|---:|---:|
| `idle >= 30s` | 71.9% | 67.2% | 69.5% |
| `keys_30s < 5` | 67.9% | 86.9% | 76.3% |
| `idle >= 30s && keys_30s < 5` | 71.9% | 67.2% | 69.5% |
| `idle >= 20s && keys_30s < 8 && no_clipboard` | **72.7%** | 78.7% | **75.6%** |

这组结果说明低活动行为确实提供了帮助需求信号，但单一 idle 阈值无法区分卡住、思考、检查和等待。当前主规则在该子集上取得了较好的 Precision/Recall 平衡，但结果仍表示“与单个标注者判断的一致程度”，不表示提示已经提高了 AC 率或学习成绩。

### 规则错误类型

主规则在该子集上的错误为：

- 误报 18 条：已经基本写完正在检查、读题或看输出、提交/判题等待、长时间离开但没有困难证据；
- 漏报 13 条：停顿未达到阈值但存在局部反复修改、短时间调试困难、仍有少量无意义输入。

因此，规则的主要问题不是发现不了“没有输入”，而是不能解释“为什么没有输入”。

## 八、从固定规则升级为两阶段方法

当前不把方法表述为“纯规则提取 + LLM 处理误报漏报”。在线时系统并不知道一个窗口到底是误报还是漏报，更准确的表述是：

```text
多规则并集 / 轻量模型
        ↓
生成高召回 Candidate
        ↓
硬保护过滤：运行、提交、失焦、剪贴板、判题等待、冷却
        ↓
轻量模型或 LLM 结合代码、行为回放和触发原因进行二次判断
        ↓
Confirmed：卡住 / 思考 / 检查 / 等待 / 离开 / 不确定
        ↓
策略层：立即提示、延迟观察、静默记录或抑制
```

### 漏报怎么处理

规则未触发的窗口不能在在线时直接被识别为漏报，因此采用“高召回 + 主动发现”的策略：

1. 使用 `keys_30s`、idle、退格后停顿、重复运行等多个规则的并集，减少单一阈值漏报；
2. 对规则未触发窗口随机抽检 5%～10%；
3. 优先抽取轻量模型预测为高风险、但规则未触发的窗口；
4. 将新发现的漏报模式转化为特征或候选规则；
5. 在新的 solution/session 上重新评估，避免只在原数据上调参。

### 为什么不直接让 LLM 实时判断

LLM 可以理解代码和行为语义，但每个按键或每个短时间片都调用会带来延迟、调用成本、隐私和输出稳定性问题。当前 AI 与人工标签的一致性也说明，LLM 更适合作为少量候选点的二次判断器，而不是第一阶段检测器或唯一决策器。两阶段方案需要通过统一离线实验验证，不能提前假设一定优于其他方法。

## 九、实验设计

### 方法对比

至少比较以下方法：

- B1：固定 `idle >= 30s`；
- B2：`keys_30s < 5`；
- B3：多规则并集；
- B4：逻辑回归；
- B5：随机森林或 XGBoost；
- B6：LLM 直接判断所有窗口；
- M1：高召回规则/轻量模型 + LLM 二次判断；
- M2：M1 + 上下文保护 + 冷却 + 恢复输入取消。

### 消融实验

- 单一 30 秒窗口 vs 多尺度窗口；
- 去掉代码进展特征；
- 去掉运行/判题上下文；
- 去掉 LLM；
- LLM 只看代码 vs 同时看行为回放和触发原因；
- 固定阈值 vs 按学生个人历史自适应阈值；
- 无冷却 vs 5/10/15 分钟冷却。

### 数据划分和指标

窗口不能随机拆分。训练、验证和测试应按 `solution_id` 划分；如果能获得学生 ID，优先按学生划分，并可增加按题目留一验证。阈值只在训练/验证集选择，最终测试集不能继续调标签和规则。

除了 Precision、Recall、F1 和 PR-AUC，还应报告：

- Candidate Recall；
- Final Precision/Recall/F1；
- 每个 session 的误提示次数；
- 每小时候选数和最终展示数；
- LLM 抑制率、每 session 调用量、平均/P95 延迟和成本；
- 提示关闭率、忽略率、恢复有效输入时间。

主评价目标建议写成：

> 在 Candidate Recall 不低于 90% 的条件下，尽量提高最终 Precision，同时降低每个 session 的误提示次数、LLM 调用量和响应延迟。

这比单独追求最高 F1 更符合主动帮助场景，因为一次误打扰可能直接打断学生的正常思考。

## 十、三个研究问题

### RQ1：候选识别

与单一 idle 规则相比，融合多尺度行为、代码进展和运行/提交上下文，能否在不使用未来信息的情况下提高帮助候选时刻的召回率？

### RQ2：误打扰控制

在保持较高 Candidate Recall 的情况下，LLM 或轻量模型二次判断能否区分“卡住”和“思考、检查、等待、离开”等状态，从而减少最终误提示？

### RQ3：系统代价与实际可用性

与纯规则、纯 LLM 判断相比，两阶段方法能否降低每个 session 的误提示次数、调用量和延迟？在 shadow mode 和后续小规模在线实验中，提示是否会带来更多恢复输入，同时不显著增加关闭、忽略和主观打扰率？

## 十一、当前限制

1. 当前样本约 100 个 session、500 条窗口，适合原型和方法比较，不足以支持复杂深度模型；
2. 现有人工标签主要来自单人标注，尚缺第二标注者和一致性报告；
3. 固定每个 session 抽取 5 个窗口与真实在线候选分布不同，后续应使用事件驱动候选验证；
4. OJ 历史数据缺少真实“学生是否希望被提示”的直接反馈；
5. 提交代码和运行上下文可能不完整，代码回放是近似表示；
6. 当前离线指标只衡量检测结果与标注判断的一致性，不能证明主动提示对成绩、AC 率或学习效果的因果影响；
7. 不同题目、学生和编程阶段的行为差异较大，固定阈值的跨人泛化仍需验证。

## 十三、汇报时可以直接这样讲

> 我研究的不是“30 秒没按键就弹窗”，而是在线编程环境中的帮助时机识别。学生没有输入可能是卡住，也可能是在思考、检查、等待或离开，所以我把问题分成候选识别、误打扰控制和系统代价三个层次。
>
> 离线阶段已经完成约 100 个 clean session、500 条严格因果窗口和 5 个时间尺度的行为特征。当前在一个独立人工评估子集上，`idle >= 20s && keys_30s < 8 && no_clipboard` 的规则达到 Precision 72.7%、Recall 78.7%、F1 75.6%，说明行为信号有效，但单一规则仍无法解释停顿原因。
>
> 因此下一步不是继续调一个固定阈值，而是采用两阶段设计：第一阶段用规则或轻量模型生成高召回候选，第二阶段结合运行上下文、代码进展和行为回放，用轻量模型或 LLM 抑制检查、等待和离开等误提示。在线先进入 shadow mode，再根据候选召回、最终 Precision、误提示次数、延迟和成本决定是否小规模展示。

## 十四、可能被问到的问题

### 1. 这是不是只是简单规则？

固定规则只是 baseline 和候选生成器。论文真正要比较的是：因果窗口、多尺度行为、代码进展、上下文过滤、两阶段判断和打扰成本能否形成更好的整体决策。

### 2. 为什么不直接调用 AI？

直接调用 AI 可以作为对照，但不适合作为每个时刻的唯一在线决策器。实时成本、延迟、隐私和不稳定性都需要纳入评价；当前 AI 与人工标签的一致性也不够支持完全替代。

### 3. 长时间 idle 到底要不要提示？

长 idle 应进入 Candidate，保证召回；但只有在确认没有运行/提交/失焦/剪贴板等上下文，并通过二次判断和冷却策略后，才考虑 Shown。这样既不把长 idle 当成确定卡住，也不会因为过度保守漏掉明显困难。

### 4. 当前结果能不能证明提示有效？

不能。当前结果只能说明检测器与人工判断的一致程度。提示是否提高恢复输入、AC 率或学习效果，需要后续 shadow mode 和带对照的在线实验。

### 5. 500 条窗口够不够？

足够完成原型、错误分析和方法对比，但不适合训练复杂模型，也不能代表所有学生和题目。论文中应把它定位为小规模离线验证，并明确后续扩展数据的计划。

## 十五、阶段性结论

目前已经完成从原始行为数据、clean session、严格因果窗口、多尺度特征、浏览器标注到规则离线评估的基本闭环。现有结果表明，低活动和停顿行为包含一定的帮助需求信号，但仅靠 idle 或按键数量无法可靠区分卡住、思考、检查和等待。

下一阶段的核心工作是提高标签可靠性，并在同一套数据和严格划分下比较规则、轻量模型、LLM 和两阶段方案。最终目标不是让系统尽可能多地弹窗，而是在高候选召回的前提下，减少真正展示给学生的误提示，并把延迟、成本和恢复行为一起纳入评价。
