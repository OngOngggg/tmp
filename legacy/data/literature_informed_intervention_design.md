# 编程学习场景的低打扰提示：离线原型设计备忘录

## 结论先行

当前原型不应把“长时间没有按键”直接等同于“学生卡住”。更稳妥的产品目标是：

> 在学生可能需要帮助、且提示不会打断高价值思考的交叉时刻，提供一次可忽略的候选提示。

因此第一版应是“注意力感知 + 状态机 + shadow mode”，而不是单阈值自动弹窗。

## 可借鉴的研究共识

### 1. 中断管理（interruption management）

人机交互研究长期强调：中断是否合适取决于用户当前任务状态和中断成本，而不是仅仅取决于系统是否有消息。用户在输入、阅读、调试关键步骤时通常不适合被打断；中断应延迟到较低成本的机会窗口。

对本项目的直接启示：

- 不在连续文本输入时弹；
- 不在编译/提交/结果展示的瞬间弹；
- 一个 idle 周期只产生一次候选；
- 使用非阻塞提示和“稍后再说”。

### 2. 注意力感知计算（attention-aware computing）

注意力不是 idle 的二元状态。阅读、思考、检查输出和离开编辑器都可能没有按键，但干预价值完全不同。系统应使用多信号估计“可打扰性”，并允许不确定。

对本项目的直接启示：

- 增加 `unknown`/`suppress` 状态；
- 长 idle 默认抑制，不直接判定需要帮助；
- 只有“低活动 + 仍在任务上下文 + 之前有活跃编码”才进入候选。

### 3. 智能辅导系统的帮助寻求（help-seeking）

教育技术中的提示通常需要遵循“最小必要帮助”原则：先给学生选择权，再逐级增加帮助强度；系统应避免替学生完成任务，也避免在学生没有准备好时强行提示。

对本项目的直接启示：

- 第一级只问“需要提示吗？”；
- 学生主动点击后再显示短提示；
- 不自动展示完整答案；
- 记录“查看提示”和“继续编写”两个分支，作为真实反馈。

### 4. 程序员工作中的上下文切换成本

编码、阅读题面、看输出、修改代码是不同活动。即使按键很少，学生可能仍处于高认知负荷阶段。系统应避免把“思考”优化成“多按键”。

对本项目的直接启示：

- 不把按键数当作学习投入度；
- `keys_30s` 只能作为低活动信号，不能单独触发；
- 需要结合编辑器是否仍聚焦、最近是否有运行/提交、是否刚出现错误结果。

## 对当前离线数据的重新解释

当前人工标签只有 182 条确定窗口，且 15/39 个 session 的窗口被全部标成同一个标签。长 idle 在这些标签中有时被标为正例，有时代表检查/阅读，因此：

- `idle >= 30 && keys_30s < 5` 可以作为“候选事件基线”；
- 不能解释为“自动弹窗规则”；
- AI 补全标签上的高 Precision 不能作为最终效果；
- 下一批标注必须给出“是否适合提示”和“当前活动类型”两个字段。

## 推荐的线上状态机

### 状态

```text
ACTIVE       最近有有效文本/编辑输入
OBSERVE      输入减少，开始观察但不提示
CANDIDATE    满足低活动和上下文条件，等待一次提示机会
SHOWN        已展示非阻塞提示
COOLDOWN     当前 idle 周期/session 暂不再提示
SUPPRESSED   提交、运行、失焦、剪贴板或其他抑制条件成立
```

### 候选条件

第一版只依赖前端可实时得到的量：

```text
idle >= 30s
keys_30s < 5
同一 idle 周期未提示
session 不在 cooldown
编辑器仍在任务上下文中
```

其中“任务上下文”至少包括：编辑器仍聚焦、没有打开帮助/结果面板、没有正在运行或提交。

### 抑制条件

任一条件成立就不提示：

- 最近 5–10 秒有连续文本输入；
- Ctrl/Meta+C/V 或大量导航键占主导；
- 刚刚提交、编译、运行或收到判题结果；
- 编辑器失焦、切换窗口或页面不可见；
- 该 idle 周期已经提示过；
- session 已达到提示上限。

## 提示的渐进式设计

```text
候选产生 -> 小型非阻塞提示 -> 学生主动点击 -> 显示一级提示
                                  -> 再次点击 -> 显示更具体的调试建议
                                  -> 忽略/关闭 -> 不再打扰
```

提示不要直接给答案，建议从以下内容开始：

- “要不要检查输入输出边界？”
- “可以先运行一个最小样例。”
- “需要查看这道题的常见错误点吗？”

## 离线评估应该改成什么

### 样本单位

从“每个 session 固定 5 个窗口”改为：

- 每个 idle 周期一个候选窗口；
- 候选前的活跃窗口作为对照；
- 提交前窗口、判题后窗口作为上下文对照；
- 随机正常输入窗口作为负样本。

### 标签

```text
helpfulness: helpful / not_helpful / unknown
activity: coding / thinking / checking / away / clipboard / stuck / unknown
```

### 指标

不要只报告窗口级 Precision/Recall，还要报告：

- 每 session 提示次数；
- 每 session 误打扰次数；
- 首次提示后继续输入的比例；
- 提示后 60/120 秒内运行或提交的比例；
- 学生主动查看提示的比例；
- session 级至少一次有效提示的比例。

## Shadow mode 和 A/B

### Shadow mode

规则触发但不展示，只记录：

- 触发时间和特征；
- 如果展示，本来会展示什么；
- 后续 30/60/120 秒是否继续输入；
- 是否运行、提交、判题以及结果。

### A/B

至少比较三组：

1. 不提示；
2. 只显示“需要提示吗？”；
3. 显示一级具体建议。

主要结果不应只看 AC 率，还要看：继续输入、提交、提示点击、关闭、重复提示和投诉/退出等行为。

## 最小可行落地

第一版只做：

1. 规则触发日志；
2. 每 idle 周期最多一次；
3. session 冷却；
4. 非阻塞提示；
5. 点击/关闭/继续输入埋点。

暂时不要做：

- 自动答案推荐；
- 依赖 `event_index / total_keys` 的规则；
- 用 AI 补全标签训练线上模型；
- 看到 idle 就强制弹窗。

## 可用于汇报的一句话

> 离线阶段将问题从“检测低按键”收敛为“在低活动且不打断高认知负荷阶段时提供可撤销帮助”，下一步先用 shadow mode 和非阻塞提示收集真实响应，再决定是否扩大触发范围。
